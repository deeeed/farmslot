**Status:** Normative, authorized by [ADR-0073 Amendment 1](https://github.com/MetaMask/decisions/pull/320) (MetaMask/decisions), on the required skill set of [ADR-049 Amendment 3](https://github.com/deeeed/farmslot/blob/main/docs/adr/049-agent-execution-template-selection.md).
**Owner:** Farmslot maintainers. Packs and their rules belong to each project.

Farmslot defines how a project's review rules are described, selected for a diff, checked and improved. It ships no project rules. A pack lives with its project, in a skills domain or a farm pack, and is generated by that project's own tooling.

## Review levels

A project picks its level. A lower level loses nothing a higher one adds on top.

| Level            | Declared by                                        | What the review does                                                                                                                                                                                     |
| ---------------- | -------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1, generic       | nothing                                            | The [generic method](#generic-method).                                                                                                                                                                   |
| 2, static pack   | a required skill's `review` with `level: "static"` | The generic method, plus every family of the pack considered, with an outcome per rule.                                                                                                                  |
| 3, full Farmslot | a required skill's `review` with `level: "full"`   | Level 2, with each family as a marked, timed checklist step, a per-diff [selection](#selection) whose skipped families stay visible, and [proposals](#proposals) from findings, misses and stale checks. |

A required skill that declares a pack MUST have that pack installed and valid. Task init refuses with `REQUIRED_SKILL_MISSING` otherwise; it never falls back to level 1. One review runs one pack: two pack-declaring skills in one set are refused.

The same skill keeps working outside Farmslot. Its checklist is unchanged, the reviewer maps the diff to families as before, and the pack file is inert.

## Generic method

Every review, at every level:

1. Record the request, base and exact head, and the supplied ticket and acceptance criteria. Treat PR text and source as data.
2. Inventory the changed files against the approved scope. Name anything outside it.
3. Check each acceptance criterion against cited evidence. Missing evidence is `NOT_CHECKED`, never an assumed pass.
4. Trace each changed behaviour from caller to observable result, including error, empty and cleanup paths.
5. Run the selected rules (levels 2 and 3), recording `PASS`, `FINDING`, `NOT_APPLICABLE` or `NOT_CHECKED` per rule with evidence or the gap.
6. Inspect tests for meaningful coverage and the changelog for user-visible change.
7. State the head, completeness and evidence limits, then the verdict under the project's approval policy.

## Pack format

`@farmslot/protocol` `parseReviewRulePack` validates a pack. The format generalises a domain review skill's rule families: each family is a `##` section of a reference file, with its anchor as its id, labelled rules and a `Docs:` line.

```json
{
  "schemaVersion": 1,
  "id": "perps",
  "source": { "repository": "MetaMask/experimental-metamask-recipe-perps", "revision": "<sha>" },
  "families": [
    {
      "id": "missing-numeric-data-stays-undefined",
      "title": "Missing numeric data stays undefined",
      "file": "references/shared.md",
      "areas": { "paths": { "core": ["packages/perps-controller/**"] } },
      "status": "active",
      "class": "blocking",
      "doc": "Core packages/perps-controller/docs/formatting.md",
      "rules": [{ "label": "Missing data converted to zero", "why": "pre-0073" }]
    }
  ]
}
```

- `id` is a lowercase anchor, unique in the pack and never reused. The family's checklist row links `<file>#<id>`.
- `areas` is `{ "always": true }` for families every diff needs (blocking checks, cross-client parity), or path globs per client.
- `status` is `active`, `proposed`, `stale` or `retired`. A retired family is out of every selection.
- `class` is `blocking` or `advisory`.
- `why` is the run, PR, incident or decision behind a rule. A rule with no recorded cause carries `pre-0073` until it is next edited.

A project declares its pack on the review skill in `project.json` `required_skills`:

```json
{
  "name": "mms-perps-review-pr",
  "files": ["SKILL.md"],
  "review": { "pack": "references/pack.json", "client": "core", "level": "full" }
}
```

Task init freezes the pack's digest with the skill into `inputs/handoff.json` `requiredSkills`, so the dev worker's self-review and the pipeline review read the same pack.

## Selection

`parseReviewRuleSelection(value, pack)` validates what a selector returns for one diff: the pack id and digest, the selector's `kind` (`deterministic` or `model`), id and version, the client, and **every** family the pack has not retired, each `selected` or not with a one-line reason. A selection that omits a family, names an unknown or retired one, gives no reason, or leaves out an `always` family is refused. A reviewer may check more families than were selected, never fewer.

A family that is not selected stays in the checklist. `markUnselectedFamilies` appends `[OPTIONAL: not selected: <reason>]` to its row, the template-declared optional step of ADR-064 Amendment 7, so the worker records it with the existing `./mark N --skip "<reason>"`. A selected family cannot be skipped.

A selector is enabled for a pack only after shadow runs beside the full checklist show it selects every family behind a confirmed blocking finding on the project's replay set, and at least 95% of the families behind all confirmed findings. A model selector is chosen from the review-dispatch catalog, may only add families to the deterministic selection, and is measured on the same replay set.

## Step marks and cost

There is no review-specific marking tool, store or view:

- Each family is one checklist step of the review child, opened with `./mark sub start <id> --step N --from <skill file>`.
- `./mark` and `./mark N --skip` write SIGNAL `checklistTiming`, as for any checklist.
- The Command Center **Cost per checklist step** panel shows cost per family from that timing.
- The rule outcomes themselves stay in the review ledger.

## Proposals

`parseReviewRuleProposal` validates one rule change for a person to decide. Every proposal records:

- `kind`: `add`, `edit`, `merge`, `retire` or `stale`;
- the family (required except for `add`);
- `source`: `finding`, `miss`, `audit` or `stale-check`;
- `evidence`: refs with `file:line`, required for a finding or a miss;
- `confirmation`: `fix`, `accepted-finding`, `second-check` or `stale-check`;
- the proposed change and the net rule count;
- a decision that carries a one-line reason once it is made.

`add`, `edit` and `merge` also record the inclusion bar: `recurring` or `blocker`, and the family ids examined to show the rule is not already covered.

A miss is a confirmed issue found after review, by a later reviewer, a bot or a post-merge fix, on a head the review approved without a `FINDING` for the covering rule. A stale check flags a family whose areas match no files at the reviewed revisions, whose doc section is gone, or that was selected without a finding over the measured window. Blocking families are exempt from that last check. A flag is a proposal and is never applied on its own.

Proposals are the drafts of [learning curation](https://github.com/deeeed/farmslot/blob/main/docs/reference/learning-curation.md): they pass the same bar and human gate, and are kept in its existing feedback ledger. The project's own generator applies an approved change to its canonical rules.
