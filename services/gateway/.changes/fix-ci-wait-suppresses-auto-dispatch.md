- Choosing wait at the `inline_fix_blocked` gate while it offers a dispatch now holds the PR: no automatic dispatch of any category and no new inline fix until the operator hands it back with an explicit `retry` or a ci-watch replay. On run fcfb5124 the operator chose wait to let MetaMask/metamask-mobile#40372 merge first; the next poll found the expected merge conflict and `merge_conflict` auto-dispatch, on by default, spawned an `update-branch` child and completed the parent in the same instant. The hold is read from `run.decisions`, so it also holds when the wait was chosen on a card a gateway restart re-presented, where no live monitor recorded it.
- While held, the merge-conflict, failed-check and both review-comment gates offer "Keep holding". The answer is stored with the PR head on GitHub and the watched failing jobs (or comment set) it was given for, so the gate stays quiet, across a restart too, until the head or the failure changes, a complete read shows that state clear (recorded on the run, so a clear before a restart counts), or the hold ends. While held, a gate whose own reads failed (the head for the conflict, the check snapshot for failed checks, the comment reads for comments) neither asks nor clears anything. An UNKNOWN mergeability read keeps a quieted conflict quiet, and a quiet conflict or a read with no head still reaches the CI wait caps. A dispatch answered at a gate before the operator's latest wait in the hold is not reused past it, and an inline fix already being delivered still finishes.
- A wait on any gate while the PR is not held, or at `inline_fix_blocked` when it offered no dispatch (a cancelled or timed-out check), keeps its one-shot meaning.
- `pr.status` reads the PR's head commit (`headRefOid`) on both the per-PR and the batched path, and lists the component reads it could not complete.
