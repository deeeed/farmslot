- A run whose `app` differs from a slot's app binding now stops at find-slot and asks the operator, even in autonomous mode. The binding is the pool slot's `app`, else the project's default app (`recipe.app`, else its only declared app); the task binding, Metro and launch actions follow it, never `run.app`. Find-slot asks when it chooses the slot, before safe reuse, a takeover or anything else touches it. The card names both apps and the slots bound to the run's app, or says they could not be listed when the status file or a pool file can't be read. Abort fails the run with nothing on the slot changed. Continue selects again, so eligibility and pressure are read afresh, then claims the slot and records `appBinding` in the find-slot outputs; a slot the operator picked stays the pick, so scoring never swaps in another, and an unpinned restart drops the preview's pressure admission so a reselect on another machine is admitted afresh. A stored answer for the same slot and apps replays, so an Abort recorded across a gateway restart still fails the run. Before, such a run froze the slot's app silently and its native proof could not run (F306: 8385c3c3 and 0ce3d071 asked for apps/sherpa-voice on Playground slots).
- `config.pools` slots carry their pool `app`.
