- Changing the operator note on a send-back no longer refuses forever. A retained delivery that was handed to the worker — typed, submitted or durably queued — is now _withdrawn by name_ in the replacement instruction, which tells the worker which of the two messages to follow if the first one still arrives, and the run records what it withdrew. One that was never attempted is simply dropped. A confirmed delivery still refuses, because the worker is known to be working from that wording and the operator should reconcile it rather than have it withdrawn underneath them.
- On run 09501e29 the feedback had reached the pane but was never confirmed, and the worker never wrote a new signal, so its instruction could neither be retried (its card had been answered another way) nor replaced. Every later send-back that worded its feedback differently was refused, with no move left for the operator. A withdrawal keeps the stale-signal allowance the retry had, so that run can be sent back.
- A handed-over delivery on a **native** host still refuses: its command sits in a durable queue nothing may cancel, so the withdrawn turn can finish and write its own terminal signal, and a withdrawal carried in a later message does not help. The operator reconciles that one.
- The stale-signal allowance follows whatever feedback was retained when the send-back started, so an edit after a replacement that never reached the composer can still send instead of failing on the signal probe.
- A withdrawal only becomes durable once its replacement is confirmed. On Claude and pi the operator send is hook-only, so a composer still holding the old text makes the replacement hold rather than type over it; overwriting the saved record first lost the retry that would have submitted the old instruction, and every later attempt held again. A replacement that is not delivered now restores the original exactly as it was, and records nothing as withdrawn.
- A send-back whose feedback reached the worker's composer but was not confirmed (`unconfirmed`) now resumes monitoring instead of re-presenting the refusal the worker is already fixing. A native `queued` command keeps its card, because the host holds it until the running turn ends and has not submitted it — resuming there would let that turn's signal end the step while the correction ran unwatched. On run 1ad82ba1 (deeeed/audiolab#526) the RPC answered `delivery is unconfirmed` while the pane had the message, the engine re-raised the same stale refusal 6 s later, and because monitoring never resumed the corrected signal the worker wrote 7 minutes later was never read — recovery took a hand-run `run.replayStep monitor`, which is what the engine now does itself. A delivery that was never attempted still keeps the decision up, because nothing reached the worker and the old refusal is still true.
- A retained instruction retires once its result has been consumed: a newer terminal signal that a completed monitor read is evidence the worker moved on, whether or not the delivery was ever confirmed. Previously only a confirmed delivery cleared, so a later refusal met an intent it could neither retry nor re-word.
