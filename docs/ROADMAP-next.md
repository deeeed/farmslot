## Current Read

Farmslot now has a first shipped replay/eval loop for evaluating agent output: worker screenshots/videos, evidence manifests, media lightboxes, artifact galleries, family observability, durable diffs, review-signal counters, retrospective learnings, Co-Pilot/log/recovery evidence surfaces, dispatch comparison lanes, a bugfix local-first publication gate, a local `#evals` Reference/Candidate cockpit, shared dispatch queue/eval slot caps, selectable worker template versions, backlog intake, roadmap-to-backlog promotion, WorkGraph orchestration/visualization, release maturity diagnostics, installed capture-helper integration, and local-first dev publication gating.

The immediate product problem is no longer landing the eval foundation; PRs #74-#78 shipped that foundation. The problem is **turning shipped eval packages into a reliable regression program**. When we adjust prompts, worker templates, recipe-runner behavior, model/runner configuration, flexible interactive-dev workflow, or the recipe protocol itself, Farmslot should be able to recreate previous PR outcomes as artifact-only Candidate packages and compare them against known-good Reference packages with diffs, visual evidence, validation evidence, review signals, time/cost, and explicit package comparison pairs. Recipe Protocol v1 (ADR-034) is **shipped** across validators, harnesses, CLI, first-party project hooks, manifest-first rendering, and local/live conformance validation — see [reference/adr-implementation-status.md](reference/adr-implementation-status.md). Remaining work is adoption by external project packs and replay/corpus use of the stable evidence contract, not protocol rollout.

This continues to extend the existing run-family/lane/run model from ADR-024 and add evals over result packages, rather than create a second top-level replay taxonomy or a separate line concept. The shipped near-term eval lane is incremental: single-case experiment/package foundation, dataset/suite/scorer boundary, local suite-builder fan-out, shared dispatch-queue slot caps, and worker-template version selection are complete; remaining gateway-owned suite history, scoring/reporting, and corpus/history surfaces wait until replay closure is reliable.

The dev-flow publication decision is no longer open: PR #96 shipped the local-first dev publication gate on top of PR #83's flexible interactive starts. Backlog Dispatch is also no longer a captured-only lane: PR #95 shipped durable backlog intake, guarded handoff into the existing queue, and a Command Center backlog surface; PRs #150/#155/#157/#160/#163 shipped the roadmap promotion and WorkGraph layer on top of it. The 2026-05-22 mobile sprint also shipped the Companion operator-control lane: authenticated gateway profiles/pairing, Android device targeting, before→after/evidence/workspace navigation hardening, fullscreen/safe-area viewer fixes, foreground voice nudge groundwork, and registered-node tmux worker discovery/control with xterm/PTY streaming. Because PRs #88-#94 decomposed many high-churn Command Center surfaces and the mobile sprint touched many high-churn phone surfaces, the immediate safe follow-up is a short UI/UX stabilization pass across newly shipped operator flows before resuming deeper replay/corpus expansion.

#### Architecture — mandatory co-located local node ([ADR-046](adr/046-mandatory-local-node.md), Proposed)

Supersedes [ADR-009 §A](adr/009-slot-workspace.md) local-bypass. Today local slots run through the gateway's `execLocal`/reimplementations and skip the node's capability layers (fs-watch, resource-watch, screen, metrics), so the gateway-host machine shows `NODE OFFLINE` in the fleet even though its slots work. Make a co-located local node mandatory: `farmslot up` supervises a loopback node so every machine (including the host) runs a node; local slots route through node RPC uniform with remote. Gateway keeps orchestration only. Sequence: (1) node lifecycle on `up` → (2) route local `exec` → (3) `fs`/watch → (4) `screen` → (5) dedup gateway reimplementations + render the local node online. Until (2) ships, the `NODE OFFLINE` badge on the local host is cosmetic.

#### Mobile — shared native build distribution (Runway-extended, Expo-Updates model)

Captured 2026-07-03 (Arthur). The per-slot mobile prepare model rebuilds/reinstalls a native dev-client per slot, which is slow and creates build/JS-version drift (a slot whose native binary or node_modules lags its checkout fails at Metro bundle — see the harness stale-deps/stale-app class). Runway already proves the better primitive: a prebuilt dev-client artifact from CI, downloaded and installed, with Metro serving JS. Extend that into a farmslot capability:

- **Build the native shell ONCE, share across many slots.** A farmslot script produces a single shared native dev-client build (iOS `.app`, Android `.apk`/package like Runway) and distributes it to every slot on the machine/fleet, instead of each slot building its own. Slots consume the shared binary + run their own isolated Metro (per-slot JS).
- **Expo-Updates mental model.** JS/bundle changes flow per-slot over Metro (fast, no native build); the shared native binary only needs rebuilding when a **native dependency** changes. The trigger is a native-dependency fingerprint (pods/Gemfile/native-module set) — when it's unchanged, all slots share the current native build and only pull JS; when it changes, one rebuild refreshes the shared artifact for all. (This is the same "detect native-dep change vs JS-only" signal the harness deps-staleness detection computes.)
- **Shared build cache (the Runway model, local-first).** The full build INTEGRATES into a shared cache rather than being per-slot-throwaway: (1) on a successful `launch ios --build`, capture the produced dev-client `.app` (and Android package); (2) key it by a native-dep FINGERPRINT (pods/Podfile.lock + native-module set + RN/Expo versions) + platform + checkout-ish marker; (3) store it in a shared local cache dir (e.g. `$FARMSLOT_HOME/build-cache/<platform>/<fingerprint>/`); (4) other slots RESOLVE-AND-PULL the cached artifact by fingerprint and `simctl install` it — no rebuild — exactly as a slot downloads a Runway prebuilt from CI. Runway (CI-produced) and the local full build become two PRODUCERS feeding the same cache/resolve contract; a slot prefers a matching cached/Runway artifact and only triggers a full build (which re-caches) when no fingerprint match exists. This is what lets a stale slot self-heal to a shared build instead of each slot rebuilding.
- **Local build overrides stale Runway (precedence).** When Runway CI hasn't published a build matching a native change yet (exactly the #32281-vs-#32678 case: Runway app predates the checkout's native surface), the operator does a manual full build and it takes PRECEDENCE in the cache — a local-built artifact shadows/overwrites a stale Runway artifact for the same platform/fingerprint. Same mental model as recipe-library precedence (personal > canonical): local manual build > Runway prebuilt when the local one is newer/matches. So a lagging Runway never blocks: build locally, it becomes the cached artifact slots pull.
- **Android parity.** Produce a shareable Android package the same way Runway does for iOS, so the shared-build model covers both platforms.
- **Why it matters:** eliminates redundant per-slot native builds (the dominant mobile prepare cost), removes the build/JS drift failure class, makes fleet mobile provisioning fast and deterministic, and gives the harness a clean warm-launch path (`launch ios` reuses the shared client) vs `--build` (rebuild the shared artifact). Ties the harness launch tiers (warm / full / runway) to a fleet-level shared-artifact lifecycle.
- **Producer = the full clean build.** A `launch ios --build` / full native build is not just a per-slot action — its output artifact becomes the **latest local cached shared build** (fingerprinted by the native-dep set). Other slots deploy that cached build instead of rebuilding; a rebuild only re-caches when the fingerprint changes. This makes the full-build path double as the shared-artifact producer (local-first; CI-produced Runway builds are the fleet/remote version of the same artifact).
- **Sequence sketch:** (1) native-dep fingerprint + "is a rebuild needed?" check → (2) one shared-build producer (iOS `.app` + Android package) → (3) fleet distribution + per-slot install → (4) per-slot Metro/JS only until fingerprint changes → (5) CI-produced shared builds (Runway generalized) so the fleet pulls prebuilt artifacts.
