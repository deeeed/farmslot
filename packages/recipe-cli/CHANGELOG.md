# Changelog

All notable changes to `@farmslot/recipe-cli` are tracked here.

## Unreleased

## 0.13.0 - 2026-10-11

- Project commands preserve resolved library provenance and validate provider options before factory construction. Managed execution carries cancellation through command and live-action children, awaits provider cancellation/finalization before success and reports every cleanup failure, and retains authored teardown, including streaming cleanup actions on a fresh cancellation context. Explicit slot selection requires a pool match before provider import. JSONL progress stays live while errors and completion wait for host closeout; superseded refusals remain in stderr diagnostics. Streaming leaves have one second to finish signal traps before escalation.

## 0.12.0 - 2026-10-11

- Resolve project providers and ordered libraries through one authorized binding and compose the shared SDK engine. Static conformance reports bind checkout and SDK code, runtime and pool selection, recipe inputs and trust; task-local code remains bound inside artifact directories. `run --plan` and conformance require mutation providers to expose read-only `trustedMutation.preflight`; missing support refuses with an upgrade hint. Recipe state stays separate from farm state, and legacy scratch-slot identities remain supported.

- Align Farmslot runtime dependencies with protocol 0.37.0 and recipe-runner 0.28.5 so consumers resolve one copy of each package.

## 0.11.4 - 2026-10-10

- Finalize the framed recorder before the completion HUD draws its result. Keep its partial video and bind the timeline to the final trace; stop using cached session screenshots once the stream reports `stream_stopped`. Reports omit unavailable frame counts and media times instead of showing zero as a measurement.

- Publish with adapter-sdk 0.8.4, agent-runtime 0.17.4, protocol 0.36.0 and recipe-runner 0.28.4 so consumers share one dependency copy.

## 0.11.3 - 2026-10-10

- A node's `cdp_port` template is read with the recipe template grammar, so `{{ params.port }}` (which the runner does not resolve) is an unresolved port instead of the port's value.
- `CAPTURE_INTERRUPTED` is an infra outcome: `run`/`call` emit it with `retryable: true` (`--json` and `--json-stream`). `run` writes report.md for any run whose recording was interrupted, product failures included, and emits its `reportPath`: `Status: evidence incomplete (capture interrupted)` when that is the only failure, an `INCOMPLETE` step and the partial video linked under `## Evidence`; and the acceptance ledger records a criterion its nodes proved as `weak` with the note `evidence incomplete (capture interrupted): …` and the partial video as evidence. A criterion whose proving node failed stays `missing`.
- Publish with adapter-sdk 0.8.3, agent-runtime 0.17.3, protocol 0.35.2 and recipe-runner 0.28.3 so consumers share one copy of each.

## 0.11.2 - 2026-10-09

- An interrupted capture-helper recording fails `run` and `call` as `CAPTURE_INTERRUPTED` (exit 4) with the partial video kept, instead of `APP_LOGIC_FAILURE` with the video deleted. The framed (Extension) recorder publishes the partial video and its timing with `interruption` in the manifest instead of failing with "Missing finalized video completion". When the run has another failed node, that failure is classified as before.
- Publish with adapter-sdk 0.8.2, agent-runtime 0.17.2, protocol 0.35.1 and recipe-runner 0.28.2 so consumers share one copy of each.

## 0.11.1 - 2026-10-09

- `run` and `call` show the automatic HUD for every recipe source and follow `--hud` (on by default, off with `--hud hide`). An untrusted or inherited source (`FARMSLOT_RECIPE_SOURCE_TRUST`) used to run without it, and `call` forced it off for every call, `--hud show` included. A platform whose `run.autoHud()` returns false still turns it off, and `call app.hud` drives the HUD itself, with no automatic updates. A call's HUD text is its `intent=` input (else a generic "Complete the requested <action> operation"), so pass `intent=` on evidence calls such as `call ui.screenshot`. The HUD is part of the plan an approval covers, so a plan approved before this change, or with another `--hud` setting, must be approved again.
- Publish with adapter-sdk 0.8.1 and recipe-runner 0.28.1 so consumers share one adapter-sdk and one recipe-runner copy.

## 0.11.0 - 2026-10-09

- `createHarnessCli` resolves one context for every public command whose grammar takes `--adapter`, `--platform` or `--target` (status, doctor, launch, run, call and the rest), and for every hidden command (its target and slot; its adapter when it sets `context: 'adapter'`). The adapter comes from, in order: the flag (`--adapter`, `--platform`, or a leading platform target such as `launch ios`), the checkout's runtime context `platform` (binding), the slot slot-config maps the checkout to (its own `platform`, when that names an adapter), a unique detect match, then the new `defaultAdapter` option. The target is `--target`, else the cwd; without `--target`, the binding, the slot and detection read the cwd's Git top level, so a subdirectory of a checkout resolves. The slot is slot-config's match (pool directory from the new `slotPoolDir` option, else FARMSLOT_POOL_DIR, else `$FARMSLOT_ROOT/pool`, else `~/farmslot-node/pool` when it exists, reported as `slot-config (~/farmslot-node/pool)`; a pool directory that exists but does not read fails the command), else the runtime context's `slotId` (the pool's slot keeps its identity beside an owned runtime context; only an explicit `--runtime-dir` runtime that names another `slotId` becomes the slot, source `binding`); with no pool directory it is reported as `{ value: null, source: 'none', detail: 'no-pool-dir' }` (`slot unknown (no pool dir)` in the human line), and when the pool maps no slot to the checkout as `{ value: null, source: 'none', detail: 'not-in-pool', poolDir }` (`slot unknown (not in ~/farmslot-node/pool)`). Approvals (`--approve-plan`, mainnet and funding flags) are never inferred. Requires `@farmslot/protocol` with `./node/slot-by-repo`: cut protocol first and re-pin the dependents.
  - The binding is the runtime context the commands read (RECIPE_RUNTIME_CONTEXT, else `<checkout>/<runtime dir>/agentic-runtime.json`), with an explicit `--runtime-dir` applied before it is read. A context binds only when its `repoRoot` is the target's Git top level (real paths), so a subdirectory of the bound checkout binds and a clone nested inside it does not. A context whose `repoRoot` is another checkout (an inherited RECIPE_RUNTIME_CONTEXT), or one without `repoRoot` outside the target, binds no adapter or slot; the context reports it as `ignoredBinding` (`path`, `repoRoot`) and the human line as `binding ignored (belongs to <root>)`.
  - Slot ports reach a command's adapter through the environment it already reads, never through its argv (the command gets exactly what was typed). For each generic port a command's grammar takes (`--cdp-port`, `--watcher-port`), when no spelling of it was typed (the option or a declared alias: `--port`, `--metro-port` for the watcher port; or any of them after `--`, where a leaf reads its own arguments) and no environment name for it holds a port, `createHarnessCli` sets `RECIPE_CDP_PORT`/`CDP_PORT`, or `RECIPE_WATCHER_PORT`/`WATCHER_PORT`/`METRO_PORT` plus each registered adapter's `devServer.portEnv`, for the invocation only (children the command spawns inherit them; `process.env` is restored exactly after dispatch, even when the command throws). Invocations of `main()` in one process run one at a time, since each sets the process-wide context and port environment; a `main()` called from inside a running command rejects at once (run the nested command as a child process) instead of waiting for itself. The port comes from the owned runtime context first (`cdpPort`; `devServerPort`, `watcherPort`, `metroPort`), then the pool slot (`cdp_port`; the dev-server `port`), so an explicit `--runtime-dir` scratch runtime fills its own ports. A typed flag, alias or passthrough port always outranks the environment in the adapters. An ignored binding fills nothing. `context.ports` (`cdp`, `watcher`) reports each: `{ source: 'flag', value? }` (no value when two spellings disagree), `{ source: 'env', value, filled: false }`, or `{ source: 'slot', value, filled: true, via: 'env', names }` (`names`: the variables set; with `invalidEnv` when a non-port value such as `RECIPE_WATCHER_PORT=abc` was replaced); the human line shows `ports cdp 9541 (slot), watcher 9400 (env, not filled)`. Adapter-specific ports stay in `context.slot.ports` for the adapter to read through `harnessContext()`. Exports `contextPorts`.
  - `--help` invocations, and hidden commands that set the new `context: 'adapter'` (shell completion), resolve the adapter too, so `call <action> --help` and completion see the checkout's adapter without `--adapter`; a tie never refuses them (they get no adapter), and they print no context line and get no filled port. Other hidden commands resolve the target and slot only and load only the plugin their flags select.
  - The `status --task` view shows the runtime context's slot and ports only when it belongs to the checkout (`runtimeContextOwned`, exported); an inherited RECIPE_RUNTIME_CONTEXT of another checkout shows nothing.
  - `status --task` and `--watch` resolve the target and slot only: no adapter is detected, refused as ambiguous or loaded. A leading platform target is read with the command's grammar (`contractPositionals`), so `launch --json android` and `launch android --json` resolve alike.
  - Detection matches the built-ins by their `detect` and the plugins the operator's libraries declare by their recipe-library.json `detect`, without importing any plugin. Only the winner is loaded, adopted and passed to `afterAdapterLoad`; a losing candidate is never imported or bound.
  - Any remote match beats any file match, and an adapter beats one it extends. More than one match left stops the command with `ADAPTER_AMBIGUOUS` (`AdapterAmbiguousError`, a `CliError`), exit 2, also when a command meets it detecting a target of its own, and the candidates (adapter, the predicates that matched, the declaring library) in the `--json` and `--json-stream` error (`candidates`) and in the human message. No match keeps the `USAGE` error and its message.
  - When the adapter was not a flag, one line on stderr names each value and its source, e.g. `context: adapter terminal (detected: remote+files), target /work/terminal-1 (cwd), slot mmt-1 (slot-config)`; `--json` and `--json-stream` print none.
  - `--json` envelopes from `status` (its task views included), `doctor`, `run`, `call`, `actions`, `run --list`/`--describe`, `call --list` and the shared usage error (`usageOut`) carry the resolved `context` (`adapter`, `target`, `slot`, each with `value`, `source` and `detail`). `launch`'s own envelope is the platform's and is unchanged.
  - Exports `resolveHarnessContext`, `formatHarnessContext`, `harnessContext`, `harnessContextField`, `contextAdapter`, `contractPositionals`, `setHarnessContext`, `declaredAdapters`, `detectAdapterMatch`, `pickDetected`, `AdapterAmbiguousError` and the `HarnessContext`, `ContextSource`, `DetectMatch`, `AdapterCandidate`, `DeclaredDetect`, `DetectEntry` and `ResolveHarnessContextOptions` types.
- `status`, `doctor`, `prepare`, the overlay commands, `resolveAdapter`, `resolveFlagsAdapter` and `task init` take an adapter no flag names from the resolved context (`contextAdapter(target)`) instead of detecting it themselves. Inside `createHarnessCli` every public command that takes those options and every hidden command has a resolved context (a `--help` invocation or a hidden command with `context: 'adapter'` gets no adapter on a tie instead of a refusal). A host that calls a handler outside `createHarnessCli` passes a flag or records a context first (`setHarnessContext(await resolveHarnessContext({ tokens }))`).
- `detectAdapter(target, declared?)` is the unique match over the registered adapters and the given plugin declarations (matched by their declared `detect`), so two matches in one pass throw `AdapterAmbiguousError` instead of the first registered winning.
- `handleStatus` takes `--adapter` and `--platform` before the context, like `doctor`. A host adds them to its `status` grammar.
- Publish with adapter-sdk 0.8.0, agent-runtime 0.17.1, protocol 0.35.0 and recipe-runner 0.28.0.

The next step says to rerun without `--record-video`, or use the adapter's own screenshot action or an adapter that records. It used to fail mid-run as `APP_LOGIC_FAILURE`; a run that still reaches the missing target now fails with `RECORDING_UNSUPPORTED`, exit 4.

It runs whenever a command selects an adapter, after the loader (a built-in or an undeclared id has no plugin record), before passthrough help, `call <action> --help`, command help and dispatch, for a host check that needs the loaded plugin (mm-harness fences a web-dapp venue policy there). ## 0.8.0 - 2026-10-07

- Bounded healing classifies a failure matching an adapter's `failurePatterns.environment` as `ENVIRONMENT_NOT_READY` (exit 4, the adapter's message and next step) instead of `APP_LOGIC_FAILURE`. `FailureClass` gains `'environment'`.

## 0.6.0 - 2026-10-06

- **BREAKING:** a run plans with a runner that has no trusted mutation. `createRunner` no longer receives the mutation `trustedMutation.load` returned for the runner that computes the plan; only the mutation `authorize` returns reaches a runner. A host whose runner reads `options.trustedMutation` during construction or preflight now sees `undefined` there; move that check to `authorize`, which receives the loaded mutation and the plan.
- `RecipeEngine.trustedMutation` hooks receive the adapter the command resolved (`--adapter`, a `--platform` target, or the detected one): `load` gets an `adapter` field, and `authorize` a third argument `{ adapter }`. Both input types are exported from `@farmslot/recipe-cli/harness` as `TrustedMutationLoadInput` and `TrustedMutationAuthorizeContext`, so a host can gate a mutation on the platform without resolving the adapter again.
  - `authorize`'s third argument is required in the type: a host that calls `engine.trustedMutation.authorize(base, plan)` itself must pass `{ adapter }`. An implementation that declares two parameters still type-checks.
  - `authorize` may return `undefined`: nothing to bind for this plan. The run then keeps the runner it planned with and executes with no trusted mutation, instead of building a second runner.
- `run` with a task dir (`RECIPE_TASK_DIR` / `FARMSLOT_TASK_DIR`) writes the task's acceptance ledger, `artifacts/acceptance-status.json` (ADR-060), from the recipe's `proofTargets`, through agent-runtime's ledger module, the one `farmslot-agent ac` uses. A target is `proven` when every node proving it passed and `missing` when one failed or did not run; `AC1` maps to the handoff's `AC-1`. Evidence is the run's `trace.json` plus the proving nodes' artifacts inside the task dir. `AC1` and `AC-1` targets count as one criterion. The run replaces the verdicts of the criteria it proves and leaves the others as they were. A target the handoff doesn't list is refused with a warning on stderr; the run's result and JSON output are unchanged.
- Static validation (`run --plan`, `validateRunRecipeStatic`) warns on two `command` node patterns whose exit code cannot prove the claim: output piped into `tail` or `head` (`recipe.command_pipe_masks_exit`; the shell reports tail's exit code, so a failing command passes), and a test command with no `assert_output` on it (`recipe.test_command_exit_code_only`; `jest -t` exits 0 when no test matches). `validateCommandNodes` is exported from `@farmslot/recipe-cli/harness`.
- Add adapter plugins to `@farmslot/recipe-cli/harness`: `ensureAdapterLoaded(id, { libraries, adopt })` loads an adapter a recipe library declares in `recipe-library.json` `adapters` when a command selects it, composes it on the adapter it `extends` (`composeAdapter`: the child's members replace the parent's; manifests, in-code action implementations and doctor checks append) and registers it with the host's adapters. `adapterChoices(libraries)` lists every id `--adapter` accepts without importing anything. A refused plugin throws `AdapterPluginError` with `ADAPTER_SDK_UNSUPPORTED`, `ADAPTER_PLUGIN_INVALID`, `ADAPTER_PLUGIN_LOAD_FAILED`, `ADAPTER_ID_CONFLICT` or `ADAPTER_EXTENDS_UNKNOWN`; `adapterSelectionFailureOut` prints it, or the library reader's `RECIPE_SOURCE_INVALID`, as the `--json` envelope.
  - Plugins load only from the operator's libraries: `--library` entries, then the `RECIPE_LIBRARY_PATH` entries they don't rename (else the personal library), then the libraries the host passes as `configured`; never from a task-local library. A host that extends `RECIPE_LIBRARY_PATH` with libraries it discovers passes the operator's environment as `env` to both `adapterChoices` and `ensureAdapterLoaded`.
  - A plugin may import from disk only the files its digest covers (its module's directory and the library's `actions/`): a `module.registerHooks` resolve hook refuses any other file with `RECIPE_SOURCE_INVALID`, while the plugin loads and while it runs. Plugin code is the module's directory plus the `actions/` files it reaches; an `actions/` file the host imports by itself isn't fenced. `node:` builtins are allowed, and a bare package resolves from the host's install (`HarnessHost.packageRoot`), never from the library's location; a package the host doesn't install, or one in a `node_modules` beside or above the library that isn't on the host's own lookup chain, is refused (a library in the host's project imports the host's packages). Loading a plugin needs Node.js 22.15 or later (`ADAPTER_PLUGIN_LOAD_FAILED` otherwise).
  - `adapterPlugin(id)` and `loadedAdapterPlugins()` describe each loaded plugin (`LoadedAdapterPlugin`: library, root, module, `extends`, and a `digest` over its library, the files under its module's directory and its parent plugin's digest), so a host can bind the actions the plugin ships in code to what a recipe approves. `adapterPluginChecks()` gives `doctor` one check per loaded plugin naming its library and digest.
  - Live action scripts follow the adapter's `extends` chain: every file of an adapter that extends another (`<actions>/<child>/<family>/<name>.mjs`, its short name, its `<family>.mjs` dispatcher) comes before any of its parent's within each actions root, and the adapter at the top of the chain keeps a built-in's order with `shared/`. Built-in adapters, which extend nothing, try exactly the files they did before, in the same order. Recipe variants don't follow `extends`.
  - `selectedAdapterId(tokens)` is the adapter a command selects, the way commands resolve it: the last `--adapter`, else the adapter of the last `--platform`. `declaredAdapterIds(sources)` reads the ids libraries declare without importing anything.
- Export `resolveTsxBin(tsxCandidates, projectRoot)` from `@farmslot/recipe-cli/harness`, the tsx lookup live adapter scripts run under (`TSX_BIN`, the checkout's tsx, the host package's tsx, the caller's candidates), so a host's readiness check can ask the same question.
